# البنشر الذكي — الإصدار التأسيسي المحسّن 0.2.0

منصة عربية/إنجليزية متجاوبة لخدمات المركبات والبنشر المتنقل والمنتجات والعروض، مبنية على Node.js وExpress وSQLite وواجهة PWA.

> **حالة المشروع بدقة:** أُضيفت وظائف وقواعد تحقق واختبارات ثابتة إلى النسخة التأسيسية. فحص صياغة JavaScript ومخطط SQL ناجحان، لكن تعذّر تثبيت تبعيات npm في بيئة الإنشاء بسبب خطأ اتصال DNS؛ لذلك لم يُشغّل خادم Express ولم تُنفّذ اختبارات HTTP متكاملة هنا. المشروع ليس معتمدًا بعد للإطلاق التجاري. اقرأ `docs/TEST_REPORT.md` قبل النشر.

## المتطلبات
- Node.js 20 أو أحدث (يفضل Node.js 22 LTS)
- npm
- تخزين دائم لملف SQLite عند النشر

## التشغيل محليًا
1. انسخ `.env.example` إلى `.env`.
2. عدّل `JWT_SECRET` إلى قيمة عشوائية قوية لا تقل عن 32 حرفًا، واضبط بريد وكلمة مرور الإدارة.
3. ثبّت الحزم: `npm install`
4. شغّل: `npm start`
5. افتح `http://localhost:3000`.
6. تحقق من `/api/health`.

في أول تشغيل فقط، ينشئ النظام حساب الإدارة إذا لم يوجد حساب مدير وكان `ADMIN_NAME` و`ADMIN_EMAIL` و`ADMIN_PASSWORD` مضبوطة. كلمة المرور يجب أن تكون 12 حرفًا على الأقل. لا تُرفع ملفات `.env` إلى GitHub. غيّر كلمة المرور بعد أول دخول، وغيّر إعدادات البيئة عند الحاجة.

## Railway + GitHub
1. ارفع محتويات المجلد إلى مستودع GitHub خاص أو مناسب.
2. أنشئ مشروعًا في Railway واربط المستودع.
3. أضف متغيرات `JWT_SECRET` و`ADMIN_NAME` و`ADMIN_EMAIL` و`ADMIN_PASSWORD` و`NODE_ENV=production`.
4. اربط Volume دائمًا، واضبط `DATABASE_PATH` إلى مسار داخل الـVolume، مثل `/data/ban-shar.db`.
5. تأكد أن أمر التشغيل `npm start` وفحص الصحة `/api/health`.
6. بعد النشر، اختبر التسجيل وتسجيل الدخول وإنشاء الطلبات وإعادة تشغيل الخدمة للتأكد من بقاء البيانات.

SQLite مناسب كبداية محدودة إذا وُضع على تخزين دائم مع نسخ احتياطية. للتوسع التشغيلي المتزامن، يُنصح بالانتقال إلى PostgreSQL مع خطة ترحيل واختبارات.

## أدوار النظام
- `customer`: إنشاء الطلبات ومتابعتها، المحادثات، التقييمات والشكاوى.
- `provider`: لا يستطيع الدخول حتى تعتمد الإدارة حسابه. يستطيع ضبط الاستعداد، قبول الطلبات وتحديثها وتقديم عروض أسعار.
- `admin`: إدارة الحسابات ومقدمي الخدمات والخدمات والمنتجات والعروض والشكاوى والإعدادات ومراجعة سجل التدقيق.

## واجهات API الأساسية
- `GET /api/health`
- `GET /api/services`, `GET /api/products`, `GET /api/offers`
- `POST /api/auth/register`, `POST /api/auth/login`, `GET /api/me`, `POST /api/auth/change-password`
- `POST /api/orders`, `GET /api/orders`, `GET /api/orders/:id`, `PATCH /api/orders/:id/status`
- `POST /api/orders/:id/accept`, `POST /api/orders/:id/quote`, `POST /api/orders/:id/quote-decision`
- `GET/POST /api/orders/:id/messages`, `POST /api/orders/:id/reviews`, `POST /api/complaints`
- `/api/provider/availability`, `/api/provider/profile`
- `/api/admin/summary`, `/api/admin/users`, `/api/admin/providers`, `/api/admin/services`, `/api/admin/products`, `/api/admin/offers`, `/api/admin/orders`, `/api/admin/orders/:id/payment`, `/api/admin/reports/summary`, `/api/admin/branches`, `/api/admin/vehicle-types`, `/api/admin/complaints`, `/api/admin/audit`, `/api/admin/settings`

كل المسارات الخاصة تتطلب `Authorization: Bearer <token>`، وتُفرض الأدوار على الخادم. أرقام هواتف العملاء لا تُرسل في بيانات الطلبات العامة لمقدم الخدمة.

## الاختبارات والتقرير
- `npm test` لفحص صياغة ملفات JavaScript وتشغيل الاختبارات الثابتة المرفقة.
- `npm run check` لفحص الصياغة الأساسية.
- راجع `docs/TEST_REPORT.md` للتمييز بين الاختبارات التي نُفذت فعلًا وتلك التي لا تزال مطلوبة.

## النسخ الاحتياطي
- اضبط `DATABASE_PATH` على ملف قاعدة البيانات الصحيح.
- نفّذ `npm run backup -- ./backups/ban-shar-backup.db` لإنشاء نسخة احتياطية متسقة عبر واجهة SQLite backup.
- اختبر الاستعادة على نسخة منفصلة قبل اعتماد أي نسخة احتياطية للإنتاج.

## وظائف إدارية إضافية في 0.2.0
- قائمة الطلبات الإدارية وتحديث حالة الدفع يدويًا مع بقاء الدفع منفصلًا عن حالة الطلب.
- ملخص تقارير الطلبات والتقييمات.
- إدارة أنواع المركبات والفروع عبر واجهات API ولوحة الإدارة.
- إشعارات داخلية مرتبطة بالحساب وإمكانية وضع علامة مقروء.
- مفتاح `Idempotency-Key` لمنع تكرار الطلب نفسه عند إعادة إرسال الطلب بالمفتاح نفسه.
- إيقاف بدء العمل إذا كان عرض السعر معلقًا أو مرفوضًا.
- فلترة الطلبات المتاحة لمقدم الخدمة بحسب الخدمات المسجلة في ملفه المهني.
- سياسة CSP أساسية وحظر بدء تشغيل الإنتاج إذا لم يُضبط سر JWT وكلمة مرور مدير فريدة.

## خطة اختبار مبدئية
- `npm run check` لفحص الصياغة الأساسية.
- `GET /api/health` للتحقق من تشغيل الخادم.
- اختبار يدوي للتسجيل، الدخول، اعتماد مقدم الخدمة، إنشاء طلب، قبوله، تحديث حالته، المحادثة والتقييم.
- اختبار المنتجات والعروض من لوحة الإدارة ثم ظهورها للعميل.
- اختبار ثبات البيانات بعد إعادة التشغيل وبعد النشر.
- اختبار الصلاحيات ومحاولات قبول الطلب نفسه بالتزامن.

لا تعتبر البنود المذكورة نتائج اختبار ناجحة إلا بعد تنفيذ الاختبار فعليًا وتسجيل نتيجته.

## قيود النسخة الحالية
- إنشاء الطلب يتطلب خدمة فعالة من القائمة؛ فهم الوصف الحر الكامل وربط الخدمة تلقائيًا يحتاج تطويرًا لاحقًا. الواجهة تحاول اقتراح الخدمة اعتمادًا على الوصف لكنها ليست ذكاءً اصطناعيًا.
- إدارة المنتجات تستخدم روابط صور؛ رفع الصور وتخزينها في خدمة ملفات مناسبة لم ينفذ بعد.
- PWA يخزن الملفات الثابتة فقط؛ الطلبات والرسائل تحتاج اتصالًا.
- إعدادات العرض الزمني تُفسر وفق توقيت قاعدة البيانات؛ يجب توحيد المنطقة الزمنية قبل الإنتاج.
- نظام تغيير كلمة المرور موجود، واستعادة كلمة المرور والتحقق من الهاتف غير منفذين.
- ينبغي إضافة اختبارات آلية وتدقيق أمني مستقل قبل إطلاق تجاري.


## تحديث: تصنيف وصف الخدمة عند إنشاء الطلب

- عند كتابة وصف مثل «تغيير الإطارات» أو «الكفر مثقوب» أو «تغيير زيت المكينة»، تقترح الواجهة الخدمة المطابقة تلقائيًا.
- النقر على بطاقة خدمة يحدد معرف الخدمة صراحةً بدل إرسال طلب غير مصنف.
- الخادم يحاول تصنيف الوصف أيضًا، لذلك لا يعتمد على الواجهة وحدها.
- يظهر اسم الخدمة المصنفة ضمن قائمة الطلبات لدى العميل ومقدم الخدمة.
- إذا لم يطابق الوصف أي خدمة، لا يُمنع العميل من الإرسال؛ يحتفظ النظام بالوصف ويعرض أن نوع الخدمة سيُحدد عند التواصل.
- التصنيف الحالي يعتمد على قواعد وكلمات مرادفة محلية، وليس على نموذج ذكاء اصطناعي خارجي.


## فصل بوابات الدخول ومراجعة مقدمي الخدمة
- `/customer` بوابة العميل: إنشاء حساب عميل بسيط برقم الهاتف وكلمة مرور، ولا تعرض لوحة مقدم الخدمة أو الإدارة.
- `/provider` بوابة مقدم الخدمة: تسجيل بالاسم والبريد الإلكتروني ورقم الهاتف وكلمة مرور، ثم تسجيل الدخول لرفع الهوية والترخيص/الوثيقة المهنية. يبقى الحساب بحالة انتظار حتى تراجع الإدارة الوثائق وتعتمده؛ لا تظهر له طلبات متاحة قبل الاعتماد وتفعيل الاستعداد.
- `/admin` بوابة الإدارة: تسجيل دخول المدير فقط. لا يوجد تسجيل مدير من الواجهة العامة.
- يحمي الخادم عمليات الإدارة بالأدوار، وتُخزن وثائق مقدمي الخدمة في مجلد خاص خارج الملفات العامة. يجب توصيل `PROVIDER_DOCUMENTS_PATH` بتخزين دائم/خاص في Railway قبل الاستخدام الحقيقي.
- يمكن للمدير إنشاء حسابات مدير إضافية من لوحة الإدارة وتغيير بريده وكلمة مروره بعد إدخال كلمة المرور الحالية.
- الحساب الإداري الأول ينشأ عند أول تشغيل فقط إذا ضُبطت متغيرات `ADMIN_NAME`, `ADMIN_EMAIL`, `ADMIN_PASSWORD` قبل التشغيل. لا تضع كلمة المرور داخل المستودع أو ملف ZIP؛ أدخلها في متغيرات البيئة، وغيّرها بعد أول دخول.
