# البنشر الذكي — منصة خدمات المركبات على الطريق

مشروع مستقل باللغة العربية واتجاه RTL، مخصص لخدمات البنشر المتنقل وبيع الإطارات والزيوت والبطاريات، وقابل لإضافة خدمات السيارات الأخرى. يتكون من ثلاث واجهات مترابطة:

- `/customer` — تطبيق العميل.
- `/provider` — تطبيق مقدم الخدمة والتسجيل الذاتي.
- `/admin` — لوحة الإدارة.

## المكونات الرئيسية الموجودة في المشروع

- واجهات متجاوبة للجوال والكمبيوتر، مع ملفات PWA مستقلة لكل بوابة وأيقونة موحدة.
- تسجيل العميل برقم الهاتف ورمز تحقق OTP؛ يمكن استخدام Twilio SMS عند ضبط بياناته، ووضع التطوير يطبع الرمز في سجل الخادم فقط.
- تسجيل ذاتي لمقدم الخدمة، رفع وثائق الهوية والصورة الشخصية ومستندات إضافية، ومراجعة الإدارة. لا يُسمح باعتماد الحساب قبل اعتماد وثيقة الهوية والصورة الشخصية.
- تحديد الخدمات والمهارات والمعدات من مقدم الخدمة، مع موافقة الإدارة على كل خدمة قبل استقبال طلباتها.
- كتالوج قابل للإدارة للخدمات وأنواع المركبات والمنتجات، ومخزون للإطارات والزيوت والبطاريات مع سعر البيع وتكلفة الشراء وحد المخزون المنخفض، ومخزون مركزي أو مرتبط بفرع.
- إنشاء طلبات، إرفاق منتجات بالطلب، حجز مخزونها عند الطلب، وإرجاع الكمية عند الإلغاء أو تعذر العثور على مقدم خدمة. يدعم أيضًا حجز موعد في فرع مع تحديد التاريخ والوقت والفرع، بشرط ربط مقدمي الخدمة بالفرع من لوحة الإدارة.
- توزيع تلقائي متسلسل: أهلية مقدم الخدمة أولًا، ثم ترتيب تقريبي وفق زمن الطريق والتقييم والإنجاز وسرعة الاستجابة والجاهزية، مع مهلة قابلة للتعديل، والانتقال إلى التالي عند الرفض أو انتهاء المهلة. يدعم النظام عروض الأسعار للخدمات التي تتطلب تسعيرًا يدويًا، ولا يسمح ببدء الخدمة قبل موافقة العميل على العرض.
- تبقى الطلبات قيد البحث حتى 10 دقائق إذا لم يكن هناك مقدم خدمة مؤهل متاح لحظة الإرسال، لتسمح بانضمام مقدم خدمة متاح لاحقًا؛ المدة قابلة للتعديل في الكود حاليًا.
- تتبع موقع مقدم الخدمة وموقع الطلب على خريطة، سجل أحداث لكل طلب، دردشة مرتبطة بالطلب، وتقييم بعد الإكمال.
- نظام شكاوى مستقل ومراسلات منفصلة بين الإدارة والعميل أو مقدم الخدمة، مع سجل تدقيق إداري. توجد فواتير قابلة للطباعة، وتسجيل يدوي لحالة الدفع ووسيلته، وتقارير مالية مبنية على الأسعار والتكاليف المسجلة.
- لوحة إحصائيات للطلبات، الرفض والمهل، مقدمي الخدمة، المناطق بحسب وصف موقع العميل، الخدمات، المخزون والتقييمات. تتضمن إدارة العملاء والفروع وأنواع المركبات.
- حماية واجهات API برمز JWT وصلاحيات الأدوار، وتجزئة كلمات المرور، وتحديد معدل بعض الطلبات، ورفع ملفات محددة الأنواع والحجم. مستندات الهوية لا تُعرض كملفات عامة؛ تنزيلها محصور بمسار إداري مصادق عليه.

## متطلبات التشغيل

- Node.js 20 أو أحدث.
- PostgreSQL 14 أو أحدث.
- حساب/خدمة SMS عند تشغيل OTP في الإنتاج.
- مزود توجيه طرق عند الحاجة إلى استخدام تجاري واسع. الإعداد الافتراضي يستخدم خدمة OSRM العامة للتجربة فقط، ويجب استبدالها أو استضافتها ذاتيًا للإنتاج.

## الإعداد المحلي

1. انسخ `.env.example` إلى `.env`، ثم أدخل رابط قاعدة بياناتك المحلية في `DATABASE_URL` عند التطوير المحلي. قيمة `DATABASE_URL` متروكة فارغة عمدًا في المثال حتى لا يُستخدم رابط localhost التجريبي بالخطأ على Railway.
2. أنشئ قاعدة PostgreSQL واضبط `DATABASE_URL`.
3. عيّن `JWT_SECRET` إلى قيمة عشوائية طويلة (32 حرفًا على الأقل).
4. عيّن `ADMIN_BOOTSTRAP_EMAIL` و`ADMIN_BOOTSTRAP_PASSWORD` و`ADMIN_BOOTSTRAP_NAME` لإنشاء المدير العام الأول. كلمة المرور يجب ألا تقل عن 12 حرفًا.
5. في التطوير المحلي فقط، اترك `NODE_ENV=development` و`OTP_MODE=console`؛ يظهر رمز OTP في سجل تشغيل الخادم. لا تستخدم ذلك في الإنتاج.
6. نفّذ:

```bash
npm install
npm start
```

ثم افتح `http://localhost:3000`.

## النشر على GitHub وRailway

1. إذا كان لديك مستودع GitHub ومشروع Railway قائم، استبدل ملفات المصدر في المجلد المرتبط بهما؛ لا تنشئ مشروعًا أو مستودعًا جديدًا.
2. تأكد من وجود خدمة PostgreSQL في مشروع Railway نفسه. لا يمكن للكود إنشاء قاعدة البيانات السحابية تلقائيًا أو معرفة رابطها السري.
3. في Variables لخدمة التطبيق، اضبط `DATABASE_URL` كمرجع لخدمة PostgreSQL. الصيغة تكون مثل `${{Postgres.DATABASE_URL}}` إذا كان اسم خدمة قاعدة البيانات `Postgres` حرفيًا؛ استخدم اسم الخدمة الفعلي. بديلًا من ذلك، اربط المتغيرات الخمسة `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE` من خدمة PostgreSQL. لا تستخدم `localhost` في الإنتاج. راجع `RAILWAY-FIX-AR.md`.
4. أضف متغيرات البيئة التالية في خدمة التطبيق:
   - `JWT_SECRET`: سر عشوائي قوي طويل.
   - `ADMIN_BOOTSTRAP_EMAIL`: البريد الذي تريد استخدامه للمدير العام أول مرة.
   - `ADMIN_BOOTSTRAP_PASSWORD`: كلمة المرور المؤقتة التي تختارها بنفسك، 12 حرفًا على الأقل.
   - `ADMIN_BOOTSTRAP_NAME`: اسم المدير العام.
   - `NODE_ENV=production`.
   - `TWILIO_ACCOUNT_SID`, `TWILIO_AUTH_TOKEN`, `TWILIO_FROM_NUMBER` لتفعيل رسائل OTP في الإنتاج.
   - `ROUTING_BASE_URL` إذا كان لديك مزود توجيه طرق آخر.
5. اجعل أمر التشغيل `npm start`. لا تحتاج إلى تحديد المنفذ يدويًا؛ يستخدم التطبيق `PORT` الذي توفره Railway.
6. إذا أردت الاحتفاظ بوثائق الهوية والصور بعد إعادة النشر، أضف Railway Volume إلى المسار `/app/uploads` (أو إلى مسار `uploads` الفعلي الذي يعمل منه التطبيق). يشمل ذلك وثائق الهوية وصور الطلبات والشعار المرفوع؛ فقرص الحاوية دون Volume قد يكون مؤقتًا.
7. بعد أول تشغيل ناجح، افتح `/admin` وسجّل الدخول بالبريد وكلمة المرور اللذين عيّنتهما في متغيرات البيئة. سيطلب منك النظام تغيير كلمة المرور المؤقتة من الإعدادات.
8. بعد تغيير كلمة المرور، يمكنك تغيير اسم الحساب وبريده وإضافة مديرين آخرين من لوحة الإدارة. لا تضع كلمات المرور الحقيقية داخل GitHub أو داخل ملفات المشروع.

### مهم بشأن حساب المدير الأول

لا توجد كلمة مرور ثابتة مخزنة في ملفات ZIP. أنت تختار البريد وكلمة المرور في متغيرات Railway قبل أول تشغيل؛ وهذا أكثر أمانًا من نشر كلمة مرور معروفة داخل المشروع. يُنشأ حساب المدير العام فقط إذا لم يكن هناك أي مدير في قاعدة البيانات.

## حدود يجب معرفتها قبل الاستخدام التجاري

- يجب إعداد Twilio أو موفر SMS فعلي لتصل رموز OTP إلى العملاء في الإنتاج.
- تتبع الموقع في هذه النسخة يعمل عندما يكون تطبيق الويب مفتوحًا ويسمح المتصفح بالموقع. متصفحات الجوال قد توقف التحديث في الخلفية أو بعد إغلاق التطبيق؛ التتبع المضمون في الخلفية يحتاج إلى تطبيق جوال أصلي أو غلاف Native مع صلاحيات الموقع المناسبة.
- يستخدم النظام خدمة OSRM العامة لتقدير الطريق افتراضيًا، وهي ليست ضمانًا لاتفاقية مستوى خدمة أو حركة مرور مباشرة. الوقت تقديري ولا يضمن بيانات ازدحام حية.
- الدفع الإلكتروني، الفواتير الضريبية المحلية، تكامل WhatsApp، تعدد العملات في بوابة الدفع، وصلاحيات إدارية دقيقة لكل مدير تحتاج إلى إعدادات وتكاملات بحسب الدولة ومزود الخدمة. لا يُدّعى أن هذه التكاملات مفعّلة دون ضبطها.
- يجب إجراء اختبار قبول شامل في بيئة Railway بقاعدة بيانات فعلية، ثم اختبار تسجيل العميل ورسائل OTP وتسجيل مقدم الخدمة واعتماده ورفع الوثائق والتوزيع التلقائي والدردشة والشكاوى والمخزون قبل تشغيل الخدمة للعامة.

## الملفات

- `server.js` — API، المصادقة، التوزيع التلقائي، الدردشة، الشكاوى، الموقع، لوحة الإدارة.
- `db/schema.sql` — مخطط قاعدة البيانات.
- `public/customer.html` و`customer.js` — بوابة العميل.
- `public/provider.html` و`provider.js` — بوابة مقدم الخدمة.
- `public/admin.html` و`admin.js` — لوحة الإدارة.
- `public/style.css` — تصميم الواجهات.
- `.env.example` — قائمة متغيرات البيئة المطلوبة.


## الهوية والإعلانات الموسمية
يمكن للمدير تعديل الاسم التجاري والاسم المختصر والشعار النصي وعنوان ووصف الصفحة الرئيسية، ورابط الشعار، وألوان الواجهة، وهاتف الدعم ورقم واتساب وبريد التواصل والعملة من لوحة الإدارة. ومن قسم «الهوية والإعلانات» يمكن إنشاء إعلانات وعروض بموعد بداية ونهاية، وصورة ورابط زر، وترتيب عرض؛ تظهر تلقائيًا خلال الفترة النشطة ويمكن تعديلها أو إيقافها أو حذفها. يمكن رفع الشعار مباشرة من لوحة الإدارة (ويُحفظ في `uploads/brand-assets`)، أو استخدام رابط HTTPS خارجي. اجعل Railway Volume مثبتًا على `/app/uploads` حتى لا يختفي الشعار المرفوع عند إعادة النشر. صور الإعلانات تُضاف كرابط صورة خارجي موثوق.
